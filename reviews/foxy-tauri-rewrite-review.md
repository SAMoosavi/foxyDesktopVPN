- [minor] src-tauri/src/lib.rs:708-712 — `handle_guardian_unauthorized` holds `inner` lock while calling `close_tunnel()`, which calls `dataplane::stop()` that joins a thread. - [minor] src-tauri/src/lib.rs:560 — `wait_while` on the Condvar returns `LockResult<MutexGuard>`, but the code calls `.unwrap_or_default()` on it. - [nit] src-tauri/src/lib.rs:376,381 — `android_tunnel::set_tun_fd` and `take_tun_fd` unwrap the OnceLock Mutex without any comment on why poisoning is impossible here. The functions are `pub` and called from Kotlin JNI glue that could panic. → Add a brief comment that these are called from Android JNI where a panic would terminate the process, so unwrap is safe (or use `expect` with a message for easier diagnosis if the invariant breaks).

- [nit] src-tauri/src/dataplane.rs:911 — The `running()` global mutex is taken during `start()` while holding the result of `ready_rx.recv()`, a cross-thread handoff. If the spawned thread panicked between sending and the recv, the join handle may already be invalid, but this code stores it anyway. The pattern is safe (the handle is `Option<JoinHandle>` and checked on `take()`), but there's no comment explaining why storing a potentially-panicked handle is deliberate. → Add a one-line note that the handle may already be done (failed setup) and that's fine; `stop()` checks `join.is_some()` before waiting.
